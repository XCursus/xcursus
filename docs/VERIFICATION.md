# Testing and verification

This document describes how XCursus is verified: which checks exist, what each one proves, how to reproduce it, and what remains unverified. Commands are run from the repository root after the installation in [DEVELOPMENT](DEVELOPMENT.md).

## Levels of verification

| Level                     | Command                                                      | Proves                                                                                                                                                 |
| ------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Static                    | `pnpm typecheck`, `pnpm lint`, `pnpm format:check`           | Strict types (including generated ones), lint rules, formatting                                                                                        |
| Unit and integration      | `pnpm test`, `pnpm test:coverage`                            | Document contract, math, navigation, renderers, archive, store, storage and CLI behaviour                                                              |
| Build and boundaries      | `pnpm build`, `pnpm check:boundaries`                        | Every package and app builds; dependency rules hold on sources and output                                                                              |
| Bundle budget             | `pnpm check:bundle`                                          | Minimal core+player consumer within 100 KiB gzip JS and 20 KiB gzip CSS                                                                                |
| Packages                  | `pnpm check:packages`                                        | Tarballs install and type-check in an external consumer; minimal and realistic consumers build                                                         |
| Browsers                  | `pnpm test:e2e`                                              | Real rendering, interaction, persistence, exports and accessibility in Chromium, Firefox and WebKit                                                    |
| Installed Chrome and Edge | `pnpm test:e2e:chrome`, `playwright.installed.config.ts`     | The same suites in an installed Chrome or Edge, or in a given build (`XCURSUS_CHANNEL`, `XCURSUS_EXECUTABLE`)                                          |
| Release checklist         | `node scripts/checklist.mjs --browser …`, `pnpm test:safari` | Items 1–6 of the release checklist through WebDriver in Safari, Firefox release builds, Safari in the iOS Simulator, and Chrome on Android through adb |
| Screen readers            | `node scripts/screen-reader.mjs --reader voiceover\|nvda`    | Item 7 with VoiceOver or NVDA driven through Guidepup, every phrase heard recorded                                                                     |
| Release checks            | `Release checks` workflow                                    | All of the above on GitHub's runners with the latest and previous stable browsers, plus informative timings                                            |
| Performance               | `pnpm benchmark`                                             | The budgets of specification §12 on the production builds, with raw samples and the environment                                                        |

A check that could not run is reported as not run, never as passed. Evidence (screenshots, round-trip JSON, measurements, axe results, exported files) is written to `test-results/` and never to tracked files.

### Coverage

`pnpm test:coverage` (V8) enforces per-area floors defined in `vitest.config.ts`:

| Area                                                    | Statements | Branches |
| ------------------------------------------------------- | ---------: | -------: |
| `packages/core/src/**`                                  |       85 % |     80 % |
| `packages/player/src/assets/**`                         |       90 % |     85 % |
| `packages/player/src/{index,content/index,messages}.ts` |       80 % |     65 % |
| `packages/plugins/src/{security,archive,media}.ts`      |       85 % |     75 % |
| `packages/editor/src/{store,storage}/**`                |       88 % |     72 % |
| `packages/impress-compat/src/**`                        |       90 % |     82 % |

Branches left uncovered are mostly DOM, focus and IndexedDB engine paths, which the browser suites exercise instead. Coverage does not replace adversarial fixtures.

### Reproducible procedures

- **Geometry.** Landmarks (scene corners, frame corners) are read with `getBoundingClientRect` and compared with `projectScenePoint` from the core; the tolerance is 1 CSS pixel.
- **Round trip.** A project is saved through a real download, reopened in a fresh browser context and compared as a model, as a camera pose and as landmarks in the player.
- **Offline HTML.** The exported file is opened from `file://` with every `http(s)` and `ws(s)` request intercepted and counted, plus offline emulation where the engine supports it with `file://`. The test requires zero requests, zero `securitypolicyviolation` events, rendered formulas, images and theme fonts, and private notes absent from source and DOM.
- **PDF.** The CLI exports the `distribution-static` fixture with `itinerary.json` (three visits) and `itinerary-repeat.json` (a repeated visit); the test checks the page count and size, extracts text with `pdftotext`, rasterizes each page and compares them (different visits differ, a repeated visit matches its first occurrence).
- **Video.** The same fixture at 30 fps: ffprobe must read the planned number of frames and the planned duration within one frame; recorded poses must equal the core sampler within 1e-6 and the rendered matrix within a relative 1e-5; two runs in the same environment produce identical frames.
- **Packages.** `pnpm check:packages` installs the tarballs in `test-results/packages/consumer` with no alias to the sources and type-checks every public API with `skipLibCheck: false`; the E2E suite then serves that consumer and runs the CLI from its installed tarball.
- **impress.js geometry.** The unit oracle builds the transform strings of `src/impress.js` 2.0.0 (`translate(-50%,-50%) translate3d() rotateX/Y/Z() scale()` for steps, the reversed inverse for the canvas, root `scale(k)` with `perspective: P/k`) and evaluates them with its own CSS arithmetic; tolerance 1e-6 relative. The browser suite reads corners with zero-size markers and `getBoundingClientRect`; the XCursus player must be within max(0.5 px, 2e-4 of the distance from the centre) of the core projection and impress.js within max(1.5 px, 5e-4 of that distance), because the upstream chain of four transforms is rounded by WebKit to about a pixel (measured worst: 0.07 px for the player in every engine, 1.12 px for impress.js in WebKit).
- **Benchmark.** `scripts/benchmark.mjs` generates the reference document (100 scenes × 10 text blocks of 100 characters, a 100-node path, no media), serves the production playground and Studio, and measures in a 1280×720 window at DPR 1: validation in Node, mount until `ready` with a fresh player, the interval between animation frames and long tasks during 10 transitions, 50 mount/destroy cycles with a counting clock and Blob URL counters plus the heap after forced GC (Chromium), and inspector input → preview commit in Studio; 5 warm-ups and 20 measurements each, p50 and p95, raw samples and the environment (CPU, memory, OS, power source, browser, commit, lockfile digest) in `test-results/benchmark/`.
- **Release checklist.** Playwright cannot drive Safari, release builds of Firefox or Chrome on a phone, so `scripts/checklist.mjs` carries out the [release checklist](RELEASE_BLOCKERS.md#manual-checklist) through a dependency-free W3C WebDriver client (`scripts/webdriver.mjs`), on the same production builds and preview servers as the suites. Items 1–5 run in Safari (safaridriver) and in Firefox release builds (geckodriver) with real clicks, keys, pointer drags, file inputs, a second window and full screen; item 6 runs with real touch input in Safari on the iOS Simulator (safaridriver) and in Chrome on Android, reached with adb and DevTools touch events. Geometry uses the same landmarks as the suites; the reopened archive is compared field by field with the saved document. Stand-ins, recorded as such: the archive download is captured in the page, the blocked pop-up is a `window.open` that returns null, offline is proven by counting remote requests; where a browser cannot read local files (Safari on the runners) file inputs are filled from the page and the exported HTML is served over http. A step the machine refuses (full screen in Safari on the runners) is recorded as not verifiable, never as passed. Results, the environment and screenshots go to `test-results/checklist/<browser>/`.
- **Screen readers.** `scripts/screen-reader.mjs` runs item 7 with NVDA and Google Chrome on Windows, and with VoiceOver and Playwright's WebKit on macOS (Safari under WebDriver suspends the session at the first key a screen reader sends). Guidepup reports what a reader says for the commands it runs, so keys go through the reader, elements focused by the page are read with the reader's own commands, and lists are entered as a user does (NVDA: Tab from the element before; VoiceOver: the VoiceOver cursor item by item). Speech spells "." as "dot" and splits camel case; names are compared accordingly. Every phrase heard is kept in `test-results/screen-reader/<reader>.json`. VoiceOver's announcement after a move is not reported through Guidepup (its last phrase stays the focused button, also with the live region given `role="status"` or made visible) and is recorded as not verifiable; NVDA reports it.
- **Browser builds.** `scripts/browser-builds.mjs` fetches the latest and previous stable Firefox (Mozilla's release archive), Chrome (Chrome for Testing) and Edge (Microsoft's package repository) for Linux; `playwright.installed.config.ts` runs every suite on a given Chrome or Edge build.
- **Release checks.** The `Release checks` workflow runs everything above on GitHub's runners: Safari 27 on macOS 15; Firefox, Chrome and Edge latest and previous on Ubuntu 24.04; the iOS Simulator on macOS 26 and the Android Emulator (API 35, Pixel 7 and Pixel Tablet) on Ubuntu with KVM; VoiceOver on macOS 15 and NVDA on Windows Server 2025, both prepared with `@guidepup/setup`; and `pnpm benchmark` on macOS 15 with windows and on Ubuntu headless, informative. Results are kept as build artifacts; the outcomes of 5 November 2026 are in the [release blockers](RELEASE_BLOCKERS.md#closed).
- **Rendering identity across builds.** `scripts/flow-identity.mjs` compares pixels and geometry of the historical fixtures between two builds of the playground; the procedure is documented in the script. It is not part of the automatic suites because it needs a second build.

## Exports and CLI

The export pipeline is verified at three levels: unit tests of the CLI (no browser), the E2E distribution suite with the CLI installed from its tarball, and checks the CLI performs on its own output and records in the `verification` field of every manifest (CSP hashes, absence of notes, page count, frame count, rendered poses). A manifest never claims a check it did not run; offline behaviour is proven only by the E2E suite.

## Legacy compatibility

Backward compatibility with SpatialDeck is verified with an archive written by SpatialDeck 0.6, kept unchanged in `tests/fixtures/legacy/layout-canvas.spatialdeck`:

- the library reads it, verifies every asset and reports its source schema version (`format.test.ts`);
- saving it again produces the same entries, manifest and asset bytes (`format.test.ts`);
- a legacy archive with a 1.2.0 document is migrated in memory and its plugin data is preserved (`format.test.ts`);
- the CLI validates it, reports `archiveFormat: "legacy"` and converts it with `pack`, leaving the original byte-for-byte unchanged (`cli.test.ts`);
- Studio opens it with a notice, saves `<title>.xcursus`, and a new session reopens that file with the same document and asset digests (`format.spec.ts`);
- the offline shell removes caches named after the former product (`pwa.spec.ts`).

Historical JSON fixtures at schema 1.0.0 (`examples/core-three-scenes`, `examples/editor-roundtrip`), 1.1.0 (`examples/structure-branching`) and 1.2.0 (`examples/content-gallery`) are opened and migrated by both the unit and the browser suites.

## Not verified and known limits

- **Browsers and devices.** The suites run in Playwright's Chromium, Firefox and WebKit and in release builds of Chrome and Edge; Safari and release builds of Firefox run the release checklist, not every suite. Touch runs on the iOS Simulator and the Android Emulator, not on physical devices; the emulator image carries Chrome 124, older than the current Chrome for Android. In Safari on the runners the file picker and `file://` are replaced by stand-ins and full screen is not verifiable; they are verified in Safari 26.5.2 on a Mac. On macOS 14 the WebKit runner paints 3D-rotated scenes flattened in screenshots while the measured geometry is correct, so WebKit assertions rely on geometry rather than pixels of 3D poses; offline emulation does not work with `file://` in that runner, where only request blocking applies.
- **Performance.** `pnpm benchmark` met every budget of the reference scenario in Chromium, Firefox and WebKit on the development Mac on battery; on GitHub's runners (no GPU) Chromium and WebKit meet the budgets and Firefox, rendering 3D in software, misses mount-ready and frame interval. The gate on a controlled machine with a GPU is still required. Long tasks are observable in Chromium only, the heap after GC is measured in Chromium only. Headless measurements of a 12-second camera spiral on a much larger deck gave p95 frame times above the 34 ms budget in Chromium and Firefox; they are pessimistic (software rendering) and must be repeated with a GPU.
- **Exports.** PDF and video are captured with Chromium only. Text of scenes seen in perspective may be rasterized in the PDF. Pixel identity of video frames holds only in the same environment. The presenter view is not available in `file://` HTML.
- **Accessibility.** axe reports no serious or critical violation, including in exported HTML (where it found the unnamed formula region fixed in the 1.0 candidate); one moderate rule (`landmark-unique`, the playground page with two players) remains. VoiceOver and NVDA are driven by automation through Guidepup, not by a person; VoiceOver's announcement after a move is not observable that way and needs a check by ear; the presenter console and the audience window are not covered by the screen reader run.
- **impress.js import.** `data-rel-position="relative"` is reported, not reproduced; CSS sizes are not evaluated; visual and timing fidelity are not claimed.
- **CI exception.** In Linux WebKit, the CSP test of `/layout` ignores `style-src-attr` reports for the two native `<select>` elements of the playground page, which are outside the player.
- **Archive memory.** `readArchive` keeps the whole compressed archive in memory in addition to the Blobs; `writeArchive` keeps the compressed chunks until the final Blob.

Open product defects found by testing are tracked in the [roadmap](ROADMAP.md#known-issues).
